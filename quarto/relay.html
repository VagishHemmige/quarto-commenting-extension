5. Apps Script relay

Author

Vagish Hemmige

The relay is a Google Apps Script web app that you deploy from your own Google account. It receives each comment, checks it, and creates the GitHub issue with your token. It is the only part that holds a secret, so it is the part to read most carefully.

NoteSource code

apps-script/Code.gs

Helpers it shares with the browser script: buildIssue_ must match issueTitle and fillPreview in issue-comments.js.

Settings

All configuration lives in Script Properties, which only you can see. Changing a property takes effect on the next request, with no redeployment.

apps-script/Code.gs, lines 1–13

/**
 * issue-comments relay: receives a reader's comment from the Quarto page and
 * files it as a GitHub issue using YOUR token. The token stays here, in
 * Script Properties, and is never sent to the browser.
 *
 * Script Properties (Project Settings > Script Properties):
 *   GITHUB_TOKEN   fine-grained token, this repo only, Issues: Read and write
 *   GITHUB_REPO    owner/repo
 *   SITE_PREFIX    optional, e.g. https://owner.github.io/repo/  (rejects other pages)
 *   PASSCODE       optional, only if you set `passcode: true` in Quarto
 *   LABEL          optional, defaults to "reader-comment"
 *   MAX_PER_HOUR   optional, defaults to 20 (all readers combined)
 */

Receiving a comment

Apps Script calls doPost for every POST to the /exec URL. Without a token and repository it refuses at once.

apps-script/Code.gs, lines 15–20

function doPost(e) {
  try {
    const props = PropertiesService.getScriptProperties();
    const token = props.getProperty("GITHUB_TOKEN");
    const repo = props.getProperty("GITHUB_REPO");
    if (!token || !repo) return reply_({ ok: false, error: "Commenting is not configured yet." });

The page sends JSON labelled as plain text (see Posting), so it is parsed by hand.

apps-script/Code.gs, line 22

const d = JSON.parse((e && e.postData && e.postData.contents) || "{}");

The checks then run cheapest first. A filled-in honeypot gets a fake success, so a bot has no reason to try again.

apps-script/Code.gs, lines 24–25

// Honeypot filled in: pretend success, do nothing.
if (d.website) return reply_({ ok: true });

apps-script/Code.gs, lines 27–30

const passcode = props.getProperty("PASSCODE");
if (passcode && d.passcode !== passcode) {
  return reply_({ ok: false, error: "That passcode is not correct." });
}

SITE_PREFIX compares the page address the browser reported. It turns away other sites and casual reuse of the URL, but the address is supplied by the sender, so it is not proof of where a request came from (see Security and privacy).

apps-script/Code.gs, lines 32–36

const prefix = props.getProperty("SITE_PREFIX");
const page = clean_(d.page, 500);
if (prefix && page.indexOf(prefix) !== 0) {
  return reply_({ ok: false, error: "Comments are not accepted from this page." });
}

The name and comment are trimmed and cut to the same limits the form uses, since a request need not come from the form.

apps-script/Code.gs, lines 38–40

const name = clean_(d.name, 80).replace(/\s+/g, " ");
const comment = clean_(d.comment, 5000);
if (!name || !comment) return reply_({ ok: false, error: "Please enter your name and a comment." });

The rate limit is checked last, so that rejected requests don’t use it up.

apps-script/Code.gs, lines 42–44

if (!allow_(Number(props.getProperty("MAX_PER_HOUR")) || 20)) {
  return reply_({ ok: false, error: "Too many comments right now. Please try again later." });
}

Then the issue is created, and the reader is sent its number and address.

apps-script/Code.gs, lines 46–48

const issue = createIssue_(token, repo, buildIssue_(d, name, comment, page),
  props.getProperty("LABEL") || "reader-comment");
return reply_({ ok: true, number: issue.number, url: issue.html_url });

Any error, including one from GitHub, is written to the Apps Script execution log for you, and the reader gets a general message, so GitHub’s response is never shown on the page.

apps-script/Code.gs, lines 49–52

} catch (err) {
  console.error(err);
  return reply_({ ok: false, error: "Something went wrong. Please try again." });
}

}

Building the issue

buildIssue_ writes the title and body. The anchor is reduced to characters valid in an id, so it cannot break out of the link. The name and section are escaped so they display literally; the passage and comment are left as typed, so GitHub renders any Markdown in them. Finally noMentions_ runs over both title and body.

apps-script/Code.gs, lines 60–81

/** The page previews this text before posting: keep issueTitle() and
 *  fillPreview() in issue-comments.js in step with any change here. */
function buildIssue_(d, name, comment, page) {
  const section = clean_(d.section, 200).replace(/\s+/g, " ");
  const anchor = clean_(d.anchor, 200).replace(/[^A-Za-z0-9_\-:.]/g, "");
  const quote = clean_(d.quote, 1600);
  const link = page + (anchor ? "#" + anchor : "");

  const firstWords = comment.replace(/\s+/g, " ").slice(0, 60) + (comment.length > 60 ? "…" : "");
  const title = (section ? "[" + section.slice(0, 60) + "] " : "") + firstWords;

  const lines = [
    "**Submitted by:** " + escapeInline_(name) + ", via the site's comment form",
    "**Section:** [" + escapeInline_(section || "Page") + "](" + link + ")",
    "",
  ];
  if (quote) {
    lines.push(quote.split("\n").map(function (l) { return "> " + l; }).join("\n"), "");
  }
  lines.push(comment);
  return { title: noMentions_(title), body: noMentions_(lines.join("\n")) };
}
WarningWhere the preview and the issue can differ

The preview’s title comes from issueTitle in the browser script, and there are two small differences from the title built here:

  • The … is added here when the comment is more than 60 characters before runs of spaces and line breaks are collapsed, and in the browser when it is more than 60 characters after. A comment a little under 60 characters that contains several line breaks can get a … in the issue but not in the preview.
  • Here the section heading has runs of spaces collapsed before it is cut to 60 characters; in the browser it is used as it is.

Neither changes what a reader wrote, only how the title is trimmed. They are noted here so that the two copies can be brought back into step.

Creating the issue

createIssue_ calls the GitHub REST API with the token and the reader-comment label (or your LABEL). muteHttpExceptions lets the code read GitHub’s error instead of Apps Script throwing its own, and anything other than 201 Created is treated as a failure.

apps-script/Code.gs, lines 83–99

function createIssue_(token, repo, issue, label) {
  const res = UrlFetchApp.fetch("https://api.github.com/repos/" + repo + "/issues", {
    method: "post",
    contentType: "application/json",
    headers: {
      Authorization: "Bearer " + token,
      Accept: "application/vnd.github+json",
      "X-GitHub-Api-Version": "2022-11-28",
    },
    payload: JSON.stringify({ title: issue.title, body: issue.body, labels: [label] }),
    muteHttpExceptions: true,
  });
  if (res.getResponseCode() !== 201) {
    throw new Error("GitHub " + res.getResponseCode() + ": " + res.getContentText().slice(0, 300));
  }
  return JSON.parse(res.getContentText());
}

The hourly limit

allow_ keeps one counter per clock hour in the script cache. The script lock stops two simultaneous requests from both reading the same count and both going through. The cache entry lasts a little over an hour (3,700 seconds), long enough to cover its hour.

apps-script/Code.gs, lines 101–115

/** Simple shared limit: at most `max` issues per rolling hour. */
function allow_(max) {
  const lock = LockService.getScriptLock();
  lock.waitLock(5000);
  try {
    const cache = CacheService.getScriptCache();
    const key = "count-" + Math.floor(Date.now() / 3600000);
    const n = Number(cache.get(key) || 0);
    if (n >= max) return false;
    cache.put(key, String(n + 1), 3700);
    return true;
  } finally {
    lock.releaseLock();
  }
}

The comment above it says “rolling hour”, but the counter resets at the top of each clock hour, so up to twice MAX_PER_HOUR can arrive within one 60-minute span that straddles the change. Google may also clear the cache early, which resets the count.

Small helpers

clean_ turns anything into a trimmed string with Unix line endings, cut to a maximum length.

apps-script/Code.gs, lines 117–119

function clean_(v, max) {
  return String(v == null ? "" : v).replace(/\r\n?/g, "\n").trim().slice(0, max);
}

noMentions_ puts an invisible zero-width space after each @ that is followed by a letter or digit. The text looks the same, but GitHub no longer sees @username, so a comment cannot notify anyone from your account.

apps-script/Code.gs, lines 122–124

function noMentions_(s) {
  return s.replace(/@(?=[A-Za-z0-9])/g, "@​");
}

escapeInline_ puts a backslash before Markdown’s special characters, so a name such as *Jane* shows as typed.

apps-script/Code.gs, lines 126–128

function escapeInline_(s) {
  return s.replace(/([\\`*_\[\]<>])/g, "\\$1");
}

reply_ sends every answer as JSON.

apps-script/Code.gs, lines 130–133

function reply_(obj) {
  return ContentService.createTextOutput(JSON.stringify(obj))
    .setMimeType(ContentService.MimeType.JSON);
}

Updating the deployment

After changing Code.gs, use Deploy → Manage deployments → Edit → Version: New version. That keeps the same /exec URL. New deployment gives a new URL, which every site using the relay would then need.
